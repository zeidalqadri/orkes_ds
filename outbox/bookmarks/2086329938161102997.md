## What the tools do

**CLIProxyAPI**: Go-based local proxy that converts OAuth subscriptions (ChatGPT, Claude, Gemini, Grok) into standard OpenAI/Gemini/Claude-compatible API endpoints. Multi-account round-robin, multi-modal support, management API. Not relevant — we don't use these subscriptions, and our agents run via `claude -p`/opencode, not through a custom proxy.

**Plugin-Deepseek-Vision**: A CLIProxyAPI v7 native plugin that:
1. Intercepts requests after auth/routing
2. Checks if the target model is in its `target_models` list (default: `deepseek-v4-flash`)
3. Uses a separate vision model (default: GPT-5.6 Luna) to analyze images
4. Replaces image blocks with structured text analysis markers + the analysis text
5. Forwards to DeepSeek — no raw images, only text
6. Agent re-analysis support (structured tool outputs for focused re-analysis of same image)
7. Fail-closed: never exposes raw images to DeepSeek

## Why this matters for arbos-

The core insight is the **preprocessing plugin pattern for non-vision models**:

```
[Image] → [Vision Model] → [Structured Text Analysis] → [DeepSeek Text Model]
```

Our fleet has DeepSeek-powered agents that receive images:
- Operator sends Telegram photos to arbos-orkes (screenshots, PM2 dashboards, error screens)
- These arrive as file paths — the model sees `[photo: /path/to/file.jpg]` but can't inspect the content
- The operator then has to describe the image contents in text, adding friction

A preprocessing layer (invoked before the prompt hits the model) would:
1. Detect image attachments in the incoming message
2. Route them to a vision-capable model (Ark's vision models, or a local one)
3. Inline the text analysis into the prompt before DeepSeek sees it
4. The DeepSeek agent then works with the full context — no operator re-description needed

## Adopt / adapt

1. **Pattern: vision-preprocessing before prompt assembly (arbos- MEDIUM)** — In `arbos.py` or the prompt assembly stage, detect image attachments in Telegram messages. Before assembling the prompt, send images to a vision-capable model (Ark API, or local ollama vision model) and inline the analysis as `[Image analysis: ...]` in the context. This is a prompt-engineering change — no new proxy infrastructure needed.

2. **Pattern: non-vision model → vision bridge as a prompt-assembly stage, not a proxy** — CLIProxyAPI does this at the HTTP proxy layer; we can do it at the prompt-assembly layer in `core/prompt.py`. Before the main model invocation, check for image references, preprocess through a vision model, inline results. Same architecture pattern, different insertion point. The plugin's configurable vision model + fallback chain is the right design.

3. **Evaluate Ark vision models for the bridge** — `~/orkes/.env` already has ARK_API_KEY. Check if `deepseek-v4-flash` on Ark supports vision natively, or if a separate vision model is available. If Ark provides a vision-capable endpoint, the bridge is zero-new-dependencies.

4. **Match the plugin's fail-closed design** — if the vision model fails, never pass raw images to DeepSeek. Include only a safe summary: `[Image attachment — unable to analyze]`. The operator can describe it manually as fallback.

## Do not adopt

- Do not install CLIProxyAPI or Plugin-Deepseek-Vision. We don't use OAuth subscriptions, and adding a Go proxy layer adds operational complexity with no benefit.
- Do not route operator photos or tender documents through external vision APIs without the operator's explicit approval — our existing sec- guardrails apply.
- Do not replace ocr-server or the webdav-intel extraction pipeline with a vision-model approach. The dedicated services work; pattern-apply the insight only to the DeepSeek-agent image gap.
