### 2. Romanescu11/hermes-skill-factory — Auto-Skill Generation from Workflow Observation

**Verdict**: HIGH

**Relevance arbos-**: HIGH. This is the most actionable item. ArbOS has 62+ skills, a `write-a-skill` skill (manual), and already records "Prior Task Trajectories (SONA)" in its prompt with similarity scores. The raw material for pattern extraction already exists — the bot sees its own past task trajectories. What's missing is a systematic pipeline: detect repeated task patterns → extract reusable steps → generate SKILL.md → register in available_skills.

**Relevance sec-**: MEDIUM. Security scraping workflows (fetch → parse → validate → store) are repetitive and would benefit from pattern detection.

**Concrete adopt**: Add a `skill-from-trajectory` subagent triggered when STATE.md task trajectories show ≥3 similar tasks (SONA score ≥0.8). It reads the trajectory, extracts the canonical workflow, and calls `write-a-skill` to generate a SKILL.md. Runs in the background after task completion (non-blocking).

**Concrete adapt**: The SONA trajectory system already captures task similarity — extend it with a "skill generation threshold" that fires when similarity count exceeds a configurable N.

### 4. witt3rd/oh-my-hermes — Deep Research + Multi-Stage Planning + Auto Triage + Autonomous Orchestration

**Verdict**: HIGH

**Relevance arbos-**: HIGH. ArbOS already has all four of these subsystems but they're disjoint:
- **Deep research**: `research-lite` subagent, web fetch, context reading
- **Multi-stage planning**: GOAP-style execution plans in STATE.md
- **Auto triage**: `triage` subagent (INTENT_ROUTING) classifies requests
- **Orchestration**: `conductor` expert dispatches to builders/testers/reviewers

The gap is **integration**. Currently these run as separate tools invoked ad-hoc by the main loop. The Hermes "commander brain" pattern — a unified planner that chains research → plan → triage → dispatch → verify in one flow — would reduce step count and eliminate conductor/builder coordination gaps.

**Relevance sec-**: LOW. Sec bots don't need multi-stage planning.

**Concrete adopt**: Add a "commander phase" to STATE.md execution plans — when a goal is complex enough (≥3 subtasks), the main loop invokes a unified `plan-research-triage-dispatch` pipeline instead of invoking each tool separately. This is essentially what the GOAP plan already describes but executed as an atomic unit.

**Concrete adapt**: The existing `conductor` expert + `triage` subagent + GOAP plan format are building blocks. Wire them together into a single `commander` subagent that takes GOAL.md → research → plan → dispatch → merge into STATE.md.

### 5. theopitori/hermeskill — Agent Runaway Detection + Apoptosis Protocol + Death Certificates

**Verdict**: HIGH

**Relevance arbos-**: HIGH. ArbOS runs in an infinite loop via pm2. The 3-strike escalation system (STATE.md) and `killclaudevandamme` skill exist but are reactive, not proactive. No formal runaway detection.

**What a runaway looks like in arbOS**: Step loop exceeding N iterations without goal completion, response token count growing exponentially (context pollution), repeated tool calls to the same failing endpoint, STATE.md growing unbounded without compress.

**Relevance sec-**: MEDIUM. Security scrapers can also go runaway (retry loops on 429, unbounded scrape depth).

**Concrete adopt**: Add a watchdog to the main loop:
1. **Step counter**: If step count > 10 without clearing GOAL.md → abort and escalate.
2. **Token budget**: If per-step token usage exceeds threshold (e.g., 20K in + 5K out) → flag and compress.
3. **Loop detection**: Hash the last 3 STATE.md summaries — if identical → abort (agent is looping).
4. **Death certificate**: On abort, write a structured `postmortem/YYYY-MM-DD-HHMM.md` with: what was the goal, what step did it fail on, what was the last state, what triggered the abort. The `postmortem` skill already exists — wire it to auto-trigger on abort.

**Concrete adapt**: The existing `killclaudevandamme` skill handles killing stale processes. Extend with the above detection logic as a pre-step gate: before each new `claude -p` invocation, run a health check against STATE.md to detect runaway.
