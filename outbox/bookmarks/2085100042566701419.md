## Verdict: MEDIUM — architecturally validates existing direction; claims are unverifiable without open code

### Relevance: arbos- MEDIUM, sec- LOW

**Why arbos- MEDIUM**:

PlugMem's core claim — "compile experience into a knowledge graph, feed agent only what matters" — overlaps with patterns we already have in production or on the roadmap:

| PlugMem claim | Our equivalent | Gap |
|---|---|---|
| Compile experience into KG | SONA trajectory similarity + shared_learnings.md | Ours is manual append, not auto-compile |
| Feed only what matters | `_prompt_safe_limit()` truncation + byte-stable prefix caching | Ours discards; PlugMem distills |
| 1-2 orders magnitude fewer tokens | DeepSeek cache-hit pricing ($0.0435/M) from @alextalksai learnings | We get savings from caching, not from distillation |
| One unchanged module | AgentDB RVF memory.db (cross-instance, schema-fixed) | Ours is queryable but not auto-compiling |

**The real gap**: within-session knowledge distillation. Our current loop is:
1. Full context loads each step (PROMPT.md + GOAL.md + STATE.md + INBOX.md + shared_learnings + MEMORY.md + cross-project memory)
2. `_prompt_safe_limit()` truncates when context overflows
3. STATE.md checkpoints key outcomes manually

PlugMem proposes: auto-compile each step's raw trajectory into a structured knowledge graph, then query it for the next step instead of re-feeding the full context. This is essentially what our SONA trajectory scores *describe* but don't yet *act on* — the trajectory exists in `context/runs/<ts>/` but is only queried for similarity, not compiled into retrievable knowledge.

**Concrete value if real**: if we could cut the pm2 loop's per-step context by even 5x (not 100x), that's:
- 5x cheaper per step (or 5x more steps for the same budget)
- Potentially faster steps (less context → faster inference)
- Auto-compiled cross-step memory without manual STATE.md writing

**Why sec- LOW**:
SEC bots (sec-agent, sec-enrich, sec-webdav-intel) are single-task specialized agents with relatively fixed prompts. The token savings from cross-step knowledge compilation would be marginal compared to arbos- bots which run long multi-step goals.

### Why NOT higher:

1. **No open implementation**: the tweet links to a video thumbnail. No paper, no repo, no code. The claims ("up to 1-2 orders of magnitude", "highest decision-utility per token of any system tested") are unverifiable without source. This could be real research or could be hype.

2. **We already have the insights**: @0xCristal's graph engineering learnings already say "structure memory as retrievable nodes, not append-only logging." @alextalksai's byte-stable caching already cuts costs 230x on cache hits. @pidotdev's harness trimming already targets context bloat. PlugMem adds the *compilation* step — auto-distill trajectory → structured facts — but that step is a refinement, not a new direction.

3. **Microsoft-only**: if PlugMem is a Microsoft-internal module (Azure/CoPilot ecosystem), it's not usable by arbos (Claude Code/OpenCode). The pattern is portable; the tool is not.

4. **Our architecture already trends this way**: bridge-memory auto-consolidates across projects. SONA scores trajectories for similarity. STATE.md is manual knowledge distillation. PlugMem's contribution is making this *automatic and per-step*, which is a quality-of-life improvement but not a capability unlock.

   When a goal completes, auto-distill the STATE.md summary into a structured shared_learnings entry (topic + source + bullet findings). Not as granular as PlugMem's per-step KG compilation, but captures the same value: "compile experience → queryable facts."
   Effort: low (~1 hour). Add to the pm2 loop's post-goal cleanup phase.
   Status: partially done (manual STATE.md updates), automate.

2. **EVALUATE: Trajectory→fact compiler for multi-step goals**
   When a goal runs 5+ steps, scan `context/runs/<ts>/` trajectories and auto-extract:

   Store as structured facts in AgentDB with backlinks to the run directory.

   This is the closest we'd come to PlugMem's "compile experience into KG" without the Microsoft module.
