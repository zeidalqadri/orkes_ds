## What it is

LoopX is an open-source framework for long-running autonomous agents (verified trajectories: 220.7h and 272.9h). Core premise: LLM context is bounded — long-range agents need externalized state, structured control, and planning to avoid drift. It provides a structured "executable Kanban" control plane:

- **Goal / Vision**: what to achieve, what must not be sacrificed by local optimization
- **Todo / Gate**: current execution frontier + decisions reserved for humans
- **Identity / Authority**: who can claim, writeback, approve
- **Evidence / Receipt**: recoverable evidence left at each step
- **Quota / Scheduler**: when to continue vs. wait
- **Handoff / Recovery**: resume after model/session/host change

The state doesn't just display status — it drives the next bounded turn. The Kanban is the execution system.

Showcases: auto PR issue fix, AutoML experiment, auto coredump fix. Agent self-evolution: discover missing capability → build it → use it within the same long-running trajectory. Build in public, Apache-2.0, integrates with Claude Code.

## Relevance: arbos-

**MEDIUM**. Arbos already implements a form of externalized state (STATE.md, GOAL.md, checkpoints, shared_learnings.md) and a structured execution plan (GOAP format in GOAL.md). The value of LoopX is NOT in implementing state management from scratch — it's in tightening the existing state from "checkpoint log" to "execution driver."

Key gaps arbos could close:

1. **State as driver, not just record**: STATE.md is currently a chronological log. While the GOAP plan in GOAL.md drives execution, STATE.md checkpoints are written AFTER work, not consulted BEFORE it. LoopX inverts this: state constraints the next bounded turn. For arbos, this means adding a `# Next Turn` section to STATE.md that explicitly declares what the next step must do before closing the current one.

2. **Domain state projection**: LoopX cleanly separates "what the external system says" (domain state) from "what the agent will do about it" (plan). Arbos mixes these — for example, "Phase 3 STAGED — needs operator window" is both a fact (domain state) and a constraint (plan). Separating them would make resumption more reliable: when arbos wakes up and reads STATE.md, it immediately sees what's externally true vs. what it planned to do about it.

3. **Explicit handoff markers**: Arbos handles session restarts by re-reading STATE.md, but there's no structured "here's what I loaded, here's what I must re-verify" protocol. LoopX's Handoff/Recovery section is explicit about resumption state. Adding a `# Resumption` block at the top of each step would harden the pm2 loop restart path.

4. **Agent self-evolution**: LoopX agents can propose → build → deploy → use new capabilities within a single trajectory. Arbos already has the `write-a-skill` and `skill-from-trajectory` patterns noted in shared_learnings (from Hermes + Skill Recorder intakes). LoopX adds the insight that this should happen within the same trajectory, not as a separate goal. Currently arbos would need a separate GOAL to create a new skill.

Integration cost is low — these are process changes to STATE.md format conventions and the pre-step resumption logic, not new tooling. No external dependency.

## Relevance: sec-

**LOW**. sec- fleet maintains scrapers and data pipelines — these are stateless, idempotent, and restartable. Multi-day agent state management is overkill for scraping operations. The one potential application is complex multi-portal scraping pipelines where external portal state (login, session, pagination cursor) determines next actions, but sec- already handles this through scraper-specific session management. The "Evidence/Receipt" pattern could tighten audit trails for long-running enrichment batches, but the value doesn't justify process overhead.

## Concrete proposals

1. **STATE.md format: add `# Next Turn` section (arbos-, immediate, zero cost)**: After writing checkpoints, add a forward-looking section that declares what the next step must do. The pm2 loop reads `STATE.md # Next Turn` before consulting `GOAL.md`. This inverts STATE.md from a log to a driver.

2. **Separate domain state from plan state (arbos-, format change)**: Add a `## Domain State` section to STATE.md for facts about external systems (e.g., "CF token unrotated", "Phase 3 staged", "journald 3.9G") that are independent of arbos's intentions. The `# Status` line and `# Next Turn` stay as arbos's interpretation and plan.

3. **Pre-step resumption protocol (arbos-, ~5 lines in engine.py)**: Before executing any goal, read STATE.md and assert: (a) `# Next Turn` exists and is ≤1 step stale, (b) `## Domain State` re-verified against live system if older than check interval, (c) escalation gates checked (step count, token budget, identical summaries). Log violations; escalate if >2 consecutively.

4. **Self-evolution within trajectory (arbos-, pattern change)**: When arbos discovers a reusable pattern during a goal, write a `skill-from-trajectory` draft BEFORE completing the goal, not as a separate post-hoc step. The trajectory is the evidence; the skill is a byproduct, not a new goal.
