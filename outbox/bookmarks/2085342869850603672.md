## Relevance Assessment

### arbos- (operational bot loop): MEDIUM

The MSW Kernel is a formal minimalism contract for agentic work:

```
contract ← requested outcome + smallest criteria that prove it
while ∃ claim c : deleting c leaves contract unmet ∨ unproven
      do c ; prove c
halt ; report
```

**Why relevant**: Our bots already encode "one clear objective per step" and "no preamble" as rules, but these are passive constraints — the model reads them and sometimes ignores them. The MSW Kernel turns minimalism into an active loop: every proposed change/step/test must survive the deletion test (if I remove this, does the contract fail?). This is a sharper, more enforceable version of what we already want.

**Why NOT high**: 
1. The specific "reinforcement line" trick ("Remember to follow the MSW deletion rule for all claims — no exceptions.") is designed for Claude 5.6 Sol max — our fleet runs DeepSeek V4 (flash/pro), where the same behavioral tics may not apply.
2. Our bots already have `step-scope-creep` as a documented recurring mistake with a prevention rule — the MSW Kernel formalizes what we already know, it doesn't reveal a new problem.
3. The MSW Kernel is ~15 lines — it's a prompt pattern, not infrastructure. Adoption is trivial; impact is bounded.

### sec- (security/scraping pipeline): LOW

sec- bots do structured, deterministic work (scrape, extract, enrich, classify). The over-engineering problem the MSW Kernel solves (models adding unnecessary artifacts/process) is less relevant to a mostly-deterministic pipeline. The deletion-test pattern is still useful for sec- code changes, but the impact is marginal compared to arbos where every step is an LLM generation.

## Adopt/Adapt/Skip Proposals

### 1. ADAPT: Contract-before-work pattern into PROMPT.md (arbos-)

Inject the MSW contract formalism into PROMPT.md's Craft Rules section:

```
## MSW Contract Rule
Before any work, state the contract: (1) requested outcome, (2) the smallest criteria that prove it.
After proposing any change, apply the deletion test: if removing this change still satisfies
the contract, skip it. No exceptions.
```

**Effort**: 5 min, edit PROMPT.md.
**Expected impact**: Reduces step-scope-creep recurrence. Complements existing "one clear objective per step" rule with an active enforcement mechanism.

### 2. ADAPT: Deletion-test as self-review gate (arbos-)

Add to the existing Craft Rules:
- "Before delivering code: for each line/function/file added, ask: does deleting it break the contract? If not, remove it."

This is the MSW `while` loop translated to a pre-commit self-check. Zero dependencies.

### 3. SKIP: Reinforcement-line trick

The specific trick — "Remember to follow the MSW deletion rule for all claims — no exceptions." — is a Sol-specific behavioral nudge. Our DeepSeek models don't exhibit the same over-engineering pathology in the same way. Including it would be cargo-cult.

### 4. EVALUATE (later): MSW Kernel for expert subagent calls

When spawning subagents (builder, reviewer, tester), append the MSW contract to the subagent's task description:
```
Contract: [specific outcome] + [acceptance criteria]
MSW rule: every claim (step, change, test) must survive the deletion test — if
removing it still satisfies the contract, skip it.
```

This is a natural fit for our expert fleet dispatch pattern — each expert gets an explicit contract, not just a task description. Worth A/B testing on a low-risk goal.

## Why Not Higher

The MSW Kernel is elegant but thin. It formalizes what experienced engineers already practice (YAGNI, minimal viable change) into a prompt pattern. For a single-operator fleet with documented step-scope-creep already, it's a refinement, not a breakthrough. The bigger wins for our fleet are in the TencentDB/PlugMem memory-layering patterns and the PrintingPress CLI-to-agent bridging — both already captured in shared_learnings.
