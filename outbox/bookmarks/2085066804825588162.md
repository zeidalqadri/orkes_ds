## Verdict: MEDIUM — architectural validation of existing memory direction; core differentiator (access control) is not our gap

### Relevance: arbos- MEDIUM, sec- LOW

**Why arbos- MEDIUM**:

TencentDB-Agent-Memory is a team-level memory hub for AI agents: converts conversations, docs, and code into four reusable asset types — Chat Memory, Skill, LLM-Wiki, CodeGraph — with versioning, access control, and cross-agent sharing. It positions itself as a "save file" for agent teams, not a chat log archive.

Our equivalents, mapped:

| TencentDB concept | Our equivalent | Gap |
|---|---|---|
| Chat Memory (L0→L1→L2→L3 layers) | AgentDB RVF memory.db + bridge-memory auto-consolidation | Ours is flat facts, theirs is layered (raw→atoms→scenarios→persona) |
| Skill (versioned workflows) | Expert fleet skills + shared_learnings.md | Ours are markdown files, theirs are versioned governed assets |
| Wiki (structured docs + link graph) | shared_learnings.md (manual append) | Ours has no link graph or versioning |
| CodeGraph (symbols, files, call relationships, impact analysis) | None | arbos has no code-level awareness between steps |
| Access control (private/team/restricted/agent) | None — all memory is open within the fleet | This is their core differentiator |
| Team sharing across frameworks | bridge-memory syncs 5 projects via SQLite | Ours works; theirs adds governance and ACL |

**The real insight: memory governance, not memory storage.**

We already have cross-instance memory sharing (AgentDB RVF), auto-consolidation (bridge-memory), semantic search (TF-IDF), and per-step trajectory storage (context/runs/). What we DON'T have is:
1. **Memory layering**: raw facts → synthesized atoms → scenario patterns → persona. We store flat facts with backlinks; they layer facts into increasing abstraction levels.
2. **Access control**: all arbos experts see all memory. TencentDB gates memory by agent/team/ACL — a supervising agent should see different memory than a scraper agent.
3. **CodeGraph**: agents have no awareness of the codebase structure between steps. Each step re-discovers which file does what.

**Why NOT higher**:

1. **Memory governance is not our bottleneck**: arbos's memory problems are context overflow (solved by `_prompt_safe_limit()` + byte-stable caching) and manual STATE.md writing (being addressed by trajectory→fact compilation from PlugMem learnings). Access control between agents in a single-operator fleet is a nice-to-have, not a capability unlock.

2. **Tencent ecosystem lock-in**: the npm package is `@tencentdb-agent-memory/memory-tencentdb` — this is Tencent's cloud product, not a self-hosted OSS tool you can `pip install`. The architecture patterns are portable; the implementation is not.

3. **We already have the insights**: @0xCristal's graph engineering learnings cover memory-as-retrievable-nodes. PlugMem learnings cover trajectory→fact auto-compilation. @EXM7777's PrintingPress covers CLI + skill auto-generation. TencentDB-Agent-Memory adds governance and layering — a refinement, not a new direction.

4. **Single-operator fleet doesn't need ACL**: arbos has one operator. Agent-to-agent memory isolation is useful for multi-tenant deployments, not for a single-operator pricing intelligence pipeline.

### Concrete Adopt/Adapt Proposals

1. **ADAPT: Memory layering for shared_learnings entries**
   Current: flat list of facts under `## Bookmark intake` / `## API & Data Shape Validation` etc.
   Proposed: add a `layer` tag to each entry — `raw` (direct observation), `synthesized` (pattern across 2+ observations), `axiom` (proven rule). When assembling prompt context, surface axioms first, then synthesized, then raw — capped at budget. This implements TencentDB's L0→L3 layering without the infrastructure.
   Effort: low (~30 min). Add a convention line to shared_learnings.md and update `_load_integration_context()` to sort by layer priority.

2. **ADAPT: CodeGraph-lite for expert dispatch**
   TencentDB's CodeGraph maps "which agent owns which file" for impact analysis. We can do a lightweight version: maintain a `## File Ownership` section in STATE.md that maps key source paths to expert domains (e.g., `cli/bids.py → builder`, `context/HARGA_CLI_REFERENCE.md → conductor`). This cuts step-1 discovery time — the conductor dispatches to the right expert without re-scanning the file tree.
   Effort: low (~15 min). One-time mapping, updated when new modules stabilize.

3. **EVALUATE: Agent-specific memory scoping**
   Currently every expert reads the full shared_learnings.md. If we tagged entries by audience (`audience: [builder, reviewer]`, `audience: [conductor]`, `audience: all`), context assembly could filter to relevant entries only — saving tokens on expert dispatch steps. This is TencentDB's "who can use it" without the access-control infrastructure.
   Effort: low (~20 min). Add audience tags + filter in prompt assembly. Worth running a 1-week A/B test against current assembly size.

4. **SKIP: TencentDB-Agent-Memory as a dependency**
   The npm package is Tencent's cloud product. Even if self-hostable, it's a Node.js/TencentDB stack — incompatible with arbos's Python/SQLite architecture. The patterns are portable; the tool is a different ecosystem. Do not attempt integration.
