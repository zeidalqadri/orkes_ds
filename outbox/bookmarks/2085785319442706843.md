# Bookmark intake — Chatpack

**Source:** @chddaniel, X post `2085785319442706843` (linked repository inspected 2026-08-08)  
**Repository:** `chddaniel/chatpack` — MIT, TypeScript monorepo; current repository status is `0.x` with active releases.

## Verdict

**MEDIUM — adopt patterns; do not install the runtime.**

| Surface | Relevance | Decision |
|---|---:|---|
| arbos- | MEDIUM | Adopt the integration-skill and durable-handoff patterns. Keep Telegram as the control surface. |
| sec- | HIGH | Reuse the notification-thread, permission, replay, and idempotency design for Harga assignments and approvals. Do not introduce Chatpack as a sidecar. |

## Why

- Chatpack has a small, explicit contract: caller-owned auth; permission hooks; durable storage; direct domain API; HTTP/SSE only as an adapter. Its durable-first mutation hook exposes all non-sender recipients, which maps cleanly to a Harga assignment or approval notification fan-out.
- Its operational details are useful: idempotent creation/mutations, monotonic per-conversation sequence numbers, reconnect replay through SSE `Last-Event-ID`, and a clear split between durable messages and ephemeral typing/presence events.
- Its agent packaging is directly reusable: a compact `SKILL.md` directs the agent to one canonical `llms.txt` contract plus verification steps. This reduces generated-code drift more reliably than scattered prompt rules.
- It is not a drop-in for the fleet: production persistence is Drizzle/Postgres, while Harga and arbos control data are SQLite/Python-first. The repository labels the API pre-1.0 and records adapter-breaking changes. A custom SQLite adapter or Node sidecar would add an unnecessary second messaging authority.
- If evaluated, disable the default anonymous telemetry explicitly and treat the outbound aggregate endpoint as disallowed unless the operator approves it.

## Concrete proposals

1. **sec- — notification-thread contract (adopt now, inside existing stack):** define one durable event record for bid/assignment/approval messages: `event_id`, `thread_id`, `actor`, `recipient`, `kind`, `payload_ref`, `seq`, `created_at`, `read_at`, `delivery_state`. Make `(thread_id, event_id)` unique; send from an outbox worker; permit retry only from the same event id. Expose `since_seq` replay to Harga vX rather than relying on browser-only state.
2. **sec- — assignment and approval fan-out (adapt):** base recipient calculation on current ownership plus role rules at mutation time, persist the recipient snapshot, then deliver email/Telegram/in-app channels independently. Do not infer recipients on retry. This makes the harga.Albert “postman” path auditable and prevents a later role change from rewriting historical intent.
3. **arbos- — skill distribution standard (adopt):** for each fleet integration with a strict contract, ship `SKILL.md` + one canonical reference + a five-command verification checklist. The skill must say when *not* to act (no secrets, no direct PM2 mutation, queue external delivery). Link it from `PROMPT.md`; do not create competing prose copies.
4. **Evaluate only if a human collaboration inbox becomes a product requirement:** run a disposable, telemetry-off compatibility spike against a scrubbed Postgres fixture. Gate promotion on authentication fit, replay correctness after reconnect, access-control tests, migration rollback, and whether it beats the native SQLite outbox. No production chat data, credentials, or browser sessions.

## Guardrails

- Keep Telegram as arbos- operator control; Chatpack does not improve the existing command/restart loop.
- Keep browser, email, and PM2 actions behind the existing approval and audit path; a conversation message is not authorization.
- Do not use in-memory storage, single-node SSE, or live-only ephemeral events for notification delivery. Reconciliation must read durable state.
