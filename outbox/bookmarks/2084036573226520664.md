## What it is

Alibaba open-sourced the code reviewer it used internally for 2 years: "Open Code Review" (Apache-2.0, 17,845 stars). It's a CLI tool that performs structured code review with:
- Line-accurate comments (claims better precision than Claude Code for the same model)
- Built-in rules: NPE, thread-safety, XSS, SQL injection
- Large changeset batching (splits into context-window-sized chunks, reviews each independently)
- OCR scan: full-file audit when the diff is too small to be meaningful
- Integrates with Claude Code, Codex, Cursor, and OpenCode

## Relevance: arbos-

**MEDIUM**. The arbos fleet already has a reviewer subagent (`opus` model, task-based dispatch) that works well for the builder+reviewer pipeline (noted as "efficient for well-scoped fix lists"). However, the premise of the tweet is architecturally valid: the current reviewer uses the same model family as the builder, which introduces reviewer bias — the thing that wrote (or is likely to produce) the bug evaluates whether it's a bug. A dedicated review tool with built-in deterministic rules (SQL injection, NPE) provides a complementary signal that doesn't share the builder's blind spots.

Key value vectors for arbos:
1. **Built-in security rules (SQL injection, XSS)** — directly relevant to harga-cli Python/SQLite code. The arbos guardrails (M2) already mandate parameterized queries, but the reviewer enforces this post-hoc via LLM, not statically. A deterministic rule would catch SQL injection before human review.
2. **Line-accurate comments** — reduces the noise of "three lines off" LLM review that forces re-reading the patch. Saves reviewer step time.
3. **OCR scan (full-file audit)** — complements diff-based review. When a change touches a function signature but not the callers, diff-only review misses downstream impact.
4. **OpenCode integration listed** — arbos runs inside OpenCode, so the tool could be invoked as a subprocess or post-patch hook.

Integration cost is the blocker: the pm2 loop drives everything via `claude -p`; wiring an external CLI tool into the review pipeline means modifying prompt.py or the task-based reviewer dispatch. This is a weekend project, not a drop-in.

## Relevance: sec-

**LOW**. sec- fleet primarily maintains scrapers and data pipelines — code changes are infrequent and small. When they do occur, the reviewer's existing security rules (SSRF, input handling) already cover scraper-specific concerns. The SQL injection / XSS rules are overkill for scraper maintenance. No adoption case that justifies integration complexity.

## Concrete proposals

1. **Rule extraction (arbos-, immediate, zero cost)**: Extract the built-in rule categories into the reviewer expert's prompt as a checklist. SQL injection, NPE-equivalent (Python NoneType), thread-safety (concurrent DB access), XSS (Flask template rendering). This improves review quality regardless of tool adoption.

2. **Monitor adoption trajectory**: The repo has 17K stars and 2 years of internal Alibaba production use — substantial signal. Track OpenCode-specific integration docs. If a 1-command install + `opencode` post-tool hook emerges, re-evaluate at MEDIUM→HIGH.

3. **Adapter pattern (if adopted)**: Wrap as a reviewer subagent pre-check step, not a replacement. The reviewer agent calls `ocr scan` on the diff, feeds structured output into its own assessment. This keeps the existing pipeline intact while adding a deterministic rule layer.

4. **Batch-splitting pattern**: Even without adopting the tool, apply the "split large changesets into context-window batches" insight to arbos review steps. If a builder produces >200 lines of diff, dispatch two sequential reviewer tasks instead of one — each gets full context focus.

## Intake classification

Signal-rich: production tool, substantial adoption, direct technical claim with benchmark. Not a credit-grab or vaporware. Keep in radar.
