# Bookmark Triage: @AISuperDomain — Microsoft Skill Recorder (2083506589793698299)

**Tweet**: @AISuperDomain, Sat Aug 01 10:54
**Topic**: Microsoft open-source "Skill Recorder" — records a human performing a task once (screen ops, window switches, web pages, clipboard, terminal commands, voice narration), then uses GitHub Copilot to convert the recording into: task intent → general steps → SKILL.md → scheduled automation.
**Links**: t.co shortlink to the Microsoft project (Scout / Copilot Cowork tooling)
**Key claim**: Not traditional RPA (no replaying mouse coordinates) — it maps web clicks to stable API / CLI / agent-native tools. Native support only for Microsoft Scout and M365 Copilot Cowork; no direct Claude Code / Codex / OpenCode support, but the emitted SKILL.md can be manually adapted.

---

## Overall Verdict: MEDIUM

The Microsoft tooling itself (screen recording, Scout, Copilot Cowork) is not directly usable — arbOS/sec run headless over SSH via pm2, no GUI session to record, and there's no native Claude Code/OpenCode support. But two **patterns** transfer cleanly and both are under-exploited in this fleet:

1. **Demo-driven skill synthesis** — capture a real successful execution and turn it into a reusable SKILL.md, rather than hand-writing skills from prose.
2. **Stable-native-over-fragile automation** — prefer API/CLI/agent-native tools over brittle positional/DOM automation (RPA coordinates, fragile CSS selectors).

## Per-Item Triage

### 1. Pattern: Demo-once → SKILL.md (record real ops → generate skill)

**Verdict**: MEDIUM-HIGH

**Relevance arbos-**: MEDIUM-HIGH. ArbOS already stores prior task trajectories (SONA similarity scoring) and has `write-a-skill` + a `skill-from-trajectory` proposal already in shared_learnings (Hermes bookmark, 2026-08-02). Skill Recorder validates that direction but adds one concrete new input signal: **capture the actual tool-call/CLI sequence of a successful run, not just the prose summary**. ArbOS's run dirs (`context/runs/<ts>/`) and `.step_msg` already record successful command traces — that is the raw "demonstration" footage. The novel adoptable idea: when a task succeeds for the N-th time with identical tool-call signatures, snapshot the exact commands into a SKILL.md template (preconditions → commands → verification) instead of a human-written description.

**Relevance sec-**: LOW-MEDIUM. sec- scrapers (webdav-intel, ePerolehan, yellowpages) have fixed, already-codified workflows; the win would be automatically recording *new* one-off scraping workflows into repeatable pipeline stages.

**Adopt**: A `skill-from-run` pass — after task completion, if the trajectory matches an existing repeated pattern (≥3 runs, SONA ≥0.8), render a SKILL.md draft from the recorded tool-call sequence (steps + exact commands + verification), then route through `write-a-skill`. Reuses existing SONA + run dirs; no new runtime deps.

**Adapt**: Treat `context/runs/` as the "recording" — add a lightweight structured log of tool-call signatures per run so trajectory → SKILL.md can be machine-extracted.

### 2. Pattern: Stable API/CLI/native tool over fragile automation

**Verdict**: HIGH (the most directly valuable takeaway)

**Relevance arbos-**: MEDIUM. Design principle for the arbos loop itself: prefer deterministic, verifiable interfaces (CLI, HTTP API, DB) over screen/DOM automation — which arbos already does (headless CLI agent). The discipline is a guardrail against drift.

**Relevance sec-**: HIGH. This is the sharpest sec- application. ePerolehan / etimad / yellowpages / webdav scrapers sit on HTML/DOM that shifts with every portal update — exactly the fragility Skill Recorder targets. Where a portal exposes a JSON API, an authenticated session, or a CLI, pin that over CSS-selector scraping. Prefer API-session login flows over UI coordinate/selector replay; degrade to DOM only when no native interface exists, and isolate selectors in one layer so portal updates touch a single module.

**Concrete adopt (sec-)**: Do a selector-drift audit on the highest-churn portals (ePerolehan, etimad, forshah): map each workflow to its most stable interface (API endpoint > CLI/session > DOM selector). Where only DOM exists, isolate selectors into a single `selectors.py` per portal so breakage is localized. Add a smoke-check that asserts key selectors still match after each portal deploy.

**Concrete adapt (arbos-)**: When a scheduled/timer task fails 2+ consecutive runs on the same step, before blind retry, re-derive the step's interface: is there an API/CLI/native alternative that removes the fragile dependency? Codify as a "fragility-first" pre-check in the watchdog's retry logic.

### 3. Item: Native-support matrix (Scout / Copilot Cowork only; no Claude Code/Codex/OpenCode)

**Verdict**: LOW (informational)

**Relevance arbos-/sec-**: LOW. The tool emits SKILL.md which is agent-agnostic, but the recorder + Copilot conversion pipeline is locked to Microsoft agents. Manual adaptation of generated SKILL.md is possible but low-yield: it duplicates what `write-a-skill` + trajectory extraction already provide natively. Note it, don't build on it.

**Why not higher**: Not a runtime dependency; no Claude Code/Codex/OpenCode support today. Revisit only if Microsoft adds an OpenCode-compatible export path.
